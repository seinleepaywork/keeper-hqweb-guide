§0 · BEFORE YOU START

작업 개시 규칙

이 문서는 참고 자료가 아니라 착수 조건이다. 아래 순서를 밟지 않은 화면은 완료로 보지 않는다.

0.1

언제 이 문서를 펴는가판단이 애매하면 해당하는 것으로 본다. 문서를 읽는 비용이 화면을 다시 만드는 비용보다 싸다.

필독

화면에 보이는 것을 새로 만들거나 고치면 전부 해당한다. 개발자와 Claude Code 모두에게 적용된다.

  • 신규 서비스·화면 추가 — 첫 줄을 쓰기 전에 §2에서 화면 유형을 고른다.
  • 기존 메뉴 개선 — 고치는 화면이 지금 어느 패턴인지 먼저 확인한다. 개선한다고 패턴을 바꾸지 않는다.
  • 컴포넌트 신설 — 배지·태그·버튼이면 §1.5와 §5 금지 #02를 먼저 본다.
  • 레이아웃·밀도 변경 — §2 두 패턴 밖으로 나가지 않는다. 제3의 밀도를 만들지 않는다.
  • 거래 문서 UI — 상태 배지나 주 행동 버튼이 걸리면 §3 상태 머신을 그대로 쓴다. 새로 정하지 않는다.
0.2

작업 순서 — 이 순서로만

5단계
  1. 화면 유형 분류 — §2의 두 패턴 중 하나로 정한다. 대시보드·원장형이면 ≥1280px 3-Pane에 행 36–40px, 포커스 문서형이면 760–840px 중앙 정렬에 인풋 40–44px. 어느 쪽인지 말하지 못하면 아직 시작하지 않은 것이다.
  2. 문서 상태 확인 — 거래 문서가 관여하면 §3 표에서 상태별 배지 토큰과 주 행동 버튼을 그대로 가져온다. 색을 새로 만들지 않는다.
  3. §1 공통 헌법 적용 — 5개 조항을 전부 적용한다. 특히 §1.2 모달 내부 인풋 금지는 대체안(인라인 편집 · 슬라이드오버 · 독립 페이지) 중 하나를 먼저 고른 뒤 만든다.
  4. §5 방지책 선탑재 — 금액 입력·배지·모달·비동기 버튼·긴 텍스트가 있으면 해당 방지책을 작성 단계에 넣는다. 리뷰에서 잡는 게 아니다.
  5. 완료 전 자기점검 — §0.4 체크리스트를 실측으로 확인한다. 눈대중은 통과가 아니다.
0.3

규격에 없는 값을 만났을 때

Hard rule

규격이 비어 있는 지점부터 구현 편차가 시작된다. 추측한 값은 화면마다 달라지고, 다음 사람이 그걸 기준으로 또 추측한다.

Forbidden
  • 없는 값을 임의로 정하고 진행하기
  • 다른 화면에서 쓰는 값을 근거 없이 복사하기
  • "일단 이렇게 두고 나중에" — 나중은 오지 않는다
Do this
  • 사람에게 질문한다 — 미결 목록에 기록을 남긴다
  • 답을 못 받고 진행해야 하면 가정한 값을 명시한다
  • 이미 알려진 미결 항목이면 그 결정을 먼저 받는다
0.4

완료 전 자기점검

실측 항목

전부 브라우저에서 수치로 확인 가능한 항목이다. 확인한 값을 보고에 적는다.

  • 모달 내부 폼 컨트롤 0개
  • alert() confirm() prompt() 0회
  • 토스트 3초 자동 소멸
  • 텍스트 컨테이너 break-keep
  • 금액·수량 셀 tabular-nums + 우측 정렬 + 3자리 콤마
  • 배지·태그·버튼 flex-shrink:0 + nowrap
  • 캔버스 #F9FAFB · 카드 1px #E5E7EB · r12
  • 인터랙티브 최소 높이 40px(모바일 44px)
  • 테이블 행 36–40px(모바일 카드 48px+)
  • 비동기 발송·신고 버튼 disabled + 스피너
  • 서체 Spoqa Han Sans Neo 1종 · 웨이트 400/500/700
  • 가로 스크롤 0px · 상시 설명문 2줄 미만
0.5

완료 보고에 반드시 적을 것

3줄
  • 분류 — 이 화면을 §2의 어느 패턴으로 만들었는지.
  • 적용 조항 — §1~§5 중 실제로 걸린 조항 번호. §5 방지책은 어느 것을 선탑재했는지.
  • 가정한 값 — 규격에 없어서 스스로 정한 값이 있으면 전부. 없으면 "없음"이라고 적는다.
§1 · CONSTITUTION

공통 헌법 — 모든 화면에서 예외 없이

새 페이지나 컴포넌트를 만들 때 아래 5개 조항은 타협 대상이 아니다.

1.1

무중단 흐름성공·저장 완료·복사 완료·네트워크 지연 모두 토스트로 전달한다. 닫기 클릭을 강제하지 않는다.

Non-disruptive
  • 작업 결과는 화면을 가로막지 않는 토스트로 전달하고 3초 후 자동 소멸시킨다.
  • 브라우저 기본 팝업 alert() confirm() prompt() 사용은 전면 금지.
1.2

모달 제약 및 인풋 전면 금지모달의 유일한 허용 목적: 영구 삭제, 국세청 즉시 신고 확정 등 불가역 파괴 액션의 2버튼 확인(Yes/No).

Hard rule

모달 안 입력창은 작성 중 이탈 시 데이터 유실 · 뷰포트 스크롤 꼬임 · 모바일 키보드 가림을 유발한다. 설계 취향 문제가 아니라 시스템 차원에서 차단하는 항목이다.

Forbidden
  • 모달 다이얼로그 내부 <input> <textarea> <select> 구현
  • 모달 안 거래처 추가 · 품목 등록 팝업
Use instead
  • 인라인 편집 — 단일·소량 수정 (테이블 셀)
  • 슬라이드오버 시트 — 복합·보조 입력 (우측 드로어)
  • 독립 포커스 페이지 — 견적서·세금계산서 빌더
1.3

점진적 정보 노출

Zero clutter
  • 폼 필드 아래나 카드 상단에 2줄 이상 상시 안내 문구를 배치하지 않는다.
  • 보조 설명은 라벨 우측 16px HelpCircle (?) 아이콘의 툴팁·팝오버로 캡슐화한다.
  • 이 페이지의 (?) 아이콘 6개가 그 패턴의 구현 예다.
1.4

타이포그래피 및 금융 데이터 표기

Typography
  • 제목·본문·UI 전반 Spoqa Han Sans Neo 단일화. 명조(세리프)·필기체 금지.
  • 웨이트 사다리는 400 / 500 / 700만 쓴다. Spoqa에는 600이 없으므로 font-weight:600은 500으로 내린다.
  • 코드·토큰 문자열만 시스템 모노(ui-monospace)를 허용한다. 본문 서체로 코드를 쓰면 열 정렬이 깨진다. 웹폰트는 추가하지 않는다.
  • 모든 텍스트 컨테이너에 word-break: keep-all overflow-wrap: break-word (Tailwind break-keep).
  • 금액·수량·세액 셀은 font-variant-numeric: tabular-nums + text-right + 3자리 콤마(1,250,000원).
  • Spoqa Han Sans Neo에는 tnum 피처가 없다. 대신 숫자 자체가 고정폭(400·500·700 모두 596/1000em 실측)이라 결과는 동일하다. 선언은 폴백 서체를 위해 유지한다.
1.5

표면 및 깊이감 — 인터콤 서피스 언어

Surface

그림자로 층을 만들지 않는다. 배경과 카드의 미세한 명도 대비 + 1px 헤어라인으로 분리한다.

§2 · LAYOUT

화면 목적별 레이아웃 패턴 & 밀도

과업 성격에 따라 화면 밀도를 두 갈래로만 분기한다. 제3의 밀도는 만들지 않는다.

대시보드 & 원장형좌측 글로벌 레일 64px + 2차 목록 280px + 메인 컨텍스트. 세부 정보는 우측 컨텍스트 드로어로 오버레이.

  • 뷰포트≥1280px 데스크톱 · 가변 그리드

  • 적용거래처 360도 관리 · 미수금/통합 문서함 · 계좌·매출매입 원장

  • 뷰포트760–840px 중앙 정렬
  • 구조A4 명세서 시각 메타포 · 단일 작업 흐름

  • 헤더좌측 '임시저장됨' 상태 + 우측 단일 메인 CTA

§4 · DIVERGENCE

의도적 차이 vs 정리 후보

다르게 생긴 화면은 두 종류다. 정당한 분기이거나, 아직 못 갚은 부채다. 섞어두지 않는다.

의도적 차이

정당한 분기
  • 인터랙션 — 데스크톱은 3패널 Co-planar + 우측 슬라이드 드로어, 모바일(<768px)은 하단 탭바 + 바텀 시트.
  • 테이블 밀도 — 데스크톱 36px 고밀도 행 유지, 터치 환경은 최소 48px 카드 리스트 뷰로 대체.

정리 후보

기술 부채
  • 레거시 모달 폼 전수 제거 — 초기 버전의 '모달 내부 거래처 추가·품목 등록' 팝업을 우측 슬라이드오버 시트로 순차 교체.
  • 인라인 스타일 변수 통일 — 하드코딩 색상값(#333 #222)을 디자인 토큰(text-gray-900 text-gray-600)으로 일괄 리팩터링.
§5 · FORBIDDEN PATTERNS

금지 패턴작성 단계에서 방어 코드를 넣는다. 리뷰에서 발견하면 이미 늦다.

아래 5개 패턴은 작성 시점에 방어 코드를 넣는다. 리뷰에서 잡는 것이 아니다.

금지 #01

금액 입력 시 쉼표 파싱 오류로 NaN 전송

방지책

모든 금액 입력 컴포넌트는 숫자만 추출해 상태에 저장하고, 포맷팅은 렌더 시점에만 적용한다.// state: 숫자만 setAmount(value.replace(/[^0-9]/g, '')) // render: 포맷은 출력 직전에만 {Number(amount).toLocaleString()}원

금지 #02

Flexbox 컨테이너 내 상태 배지 찌그러짐

방지책

모든 배지·태그·버튼 컴포넌트에 flex-shrink-0 whitespace-nowrap을 기본 탑재한다. 옵션이 아니라 기본값.

금지 #03

모달 폼 작성 중 바깥 클릭으로 전체 데이터 증발

방지책

모달 내부 인풋 전면 금지(§1.2). 모든 입력 폼은 자동 임시저장(Local auto-save)과 닫기 전 변경사항 경고를 필수 적용한다.

금지 #04

비동기 발행 버튼 연타로 중복 요청 전송

방지책

모든 비동기 발송·신고 버튼은 클릭 즉시 disabled + 내부 스피너를 표시하고 요청 완료까지 클릭 이벤트를 차단한다. 이 페이지 §6의 복사 버튼이 그 구현 예다.

금지 #05

좁은 화면에서 단어가 조사 단위로 쪼개짐

방지책

모든 텍스트 엘리먼트에 break-keep을 공통 적용한다. 예외는 코드·URL 블록뿐.

## 0. Before You Start (READ THIS FIRST)
- TRIGGER: any new screen/service, any menu improvement, any new component, any layout or
  density change, any transaction-document UI. If it renders, this applies.
- Do NOT write UI code before you have (a) picked the screen pattern and (b) read §1 of the UX guide.
- Order: 1) classify screen type → 2) lock document state badges/CTA → 3) apply the 5 constitution
  rules → 4) pre-load the incident guards → 5) verify the self-check list by measurement.
- If a spec value is MISSING: never invent one. Add it to the open-items list and ask.
  If you must proceed, state the assumed value explicitly in your report.
- Report must state: which screen pattern, which rule sections applied, which values you assumed.
- 전문: docs/UX_GUIDE.md §0. 이 절은 그 요약이다.

## 1. Absolute Constraints (Zero Tolerance)
- FORBIDDEN: NEVER build form controls (`<input>`, `<textarea>`, `<select>`) inside Modal Dialogs.
- Modals are strictly for two-button confirmation of irreversible destructive actions (Delete, Final IRS Submit).
- For form inputs, use: (1) Inline editable cells, (2) Right-side Slide-over Sheets, or (3) Dedicated full pages.
- NEVER use native blocking alerts (`window.alert`, `window.confirm`). Use Toast notifications (auto-dismiss 3s).

## 2. Korean Typography & Numeric Rules
- All Korean text containers MUST include `word-break: keep-all; overflow-wrap: break-word;` (Tailwind: `break-keep`).
- Font family is strictly `Spoqa Han Sans Neo` (SIL OFL 1.1). No serif/cursive fonts.
- Weight ladder is 400 / 500 / 700 only. Spoqa has no 600 — map `font-weight:600` to 500.
- Only code/token strings may use `ui-monospace`. Never add another webfont.
- Financial numbers in tables/cards MUST use `font-variant-numeric: tabular-nums`, right alignment (`text-right`),
  and 3-digit commas (`1,000,000원`).

## 3. Zero Clutter & Progressive Disclosure
- NEVER render multi-line static explanatory text directly under labels.
- Secondary descriptions MUST be wrapped inside a 16px `HelpCircle` icon triggering a Tooltip or Popover.

## 4. Visual Tokens & Surface Language
- Canvas Background: `#F9FAFB` (Off-white canvas). Pure white `#FFFFFF` for page background is prohibited.
- Cards & Surfaces: `#FFFFFF` with `border: 1px solid #E5E7EB` and `border-radius: 12px`. Drop shadows minimal.
- Touch Targets: Interactive elements must have a minimum height >= 40px (Mobile >= 44px).
- Badges & Tags: Always set `flex-shrink: 0; white-space: nowrap;` to prevent layout collapse.
- Light theme ONLY. Declare `color-scheme: light`. Never add a dark palette or `prefers-color-scheme` block.

## 5. Defensive Engineering & Safety
- Currency inputs must safely strip commas before numeric parsing to prevent `NaN` bugs.
- API submission buttons MUST implement debounce and display loading spinners with `disabled` states.
- Long-form document editors must feature automatic local draft saving.

> 아래 6·7절은 원문 룰셋 블록에 없던 확장이다. 본 문서 §3·§2에서 파생했다.

## 6. Document State Machine
- Draft → Sent → Viewed → Signed → Paid → Reported
- Badge tokens are fixed per state; do not invent new status colors.
  Draft    bg-gray-100 / text-gray-700       Signed   bg-teal-50 / text-teal-700
  Sent     bg-blue-50 / text-blue-700        Paid     bg-emerald-50 / text-emerald-700
  Viewed   bg-purple-50 / text-purple-700    Reported bg-green-100 / text-green-800

## 7. Layout Density
- Dashboard / Ledger screens: >=1280px, 64px global rail + 280px list + main, table rows 36-40px.
- Focused Document screens: 760-840px centered, input height 40-44px, single primary CTA in header.
- Mobile (<768px): bottom tab bar + bottom sheet, card list rows >=48px.
