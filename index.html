§0 · BEFORE YOU START

작업 개시 규칙

이 문서는 참고 자료가 아니라 착수 조건이다. 아래 순서를 밟지 않은 화면은 완료로 보지 않는다.

0.1

언제 이 문서를 펴는가판단이 애매하면 해당하는 것으로 본다. 문서를 읽는 비용이 화면을 다시 만드는 비용보다 싸다.

필독

화면에 보이는 것을 새로 만들거나 고치면 전부 해당한다. 개발자와 Claude Code 모두에게 적용된다.

  • 신규 서비스·화면 추가 — 첫 줄을 쓰기 전에 §2에서 화면 유형을 고른다.
  • 기존 메뉴 개선 — 고치는 화면이 지금 어느 패턴인지 먼저 확인한다. 개선한다고 패턴을 바꾸지 않는다.
  • 컴포넌트 신설 — 배지·태그·버튼이면 §1.5와 §5 금지 #02를 먼저 본다.
  • 레이아웃·밀도 변경 — §2 두 패턴 밖으로 나가지 않는다. 제3의 밀도를 만들지 않는다.
  • 거래 문서 UI — 상태 배지나 주 행동 버튼이 걸리면 §3 상태 머신을 그대로 쓴다. 새로 정하지 않는다.
0.2

작업 순서 — 이 순서로만

5단계
  1. 화면 유형 분류 — §2의 두 패턴 중 하나로 정한다. 대시보드·원장형이면 ≥1280px 3-Pane에 행 36–40px, 포커스 문서형이면 760–840px 중앙 정렬에 인풋 40–44px. 어느 쪽인지 말하지 못하면 아직 시작하지 않은 것이다.
  2. 문서 상태 확인 — 거래 문서가 관여하면 §3 표에서 상태별 배지 토큰과 주 행동 버튼을 그대로 가져온다. 색을 새로 만들지 않는다.
  3. §1 공통 헌법 적용 — 9개 조항을 전부 적용한다. 특히 §1.2 모달 내부 인풋 금지는 대체안(인라인 편집 · 슬라이드오버 · 독립 페이지) 중 하나를 먼저 고른 뒤 만든다.
  4. §5 금지 패턴 선탑재 — 금액 입력·배지·모달·비동기 버튼·긴 텍스트가 있으면 해당 방지책을 작성 단계에 넣는다. 리뷰에서 잡는 게 아니다.
  5. 완료 전 자기점검 — §0.4 체크리스트를 실측으로 확인한다. 눈대중은 통과가 아니다.
0.3

규격에 없는 값을 만났을 때

Hard rule

규격이 비어 있는 지점부터 구현 편차가 시작된다. 추측한 값은 화면마다 달라지고, 다음 사람이 그걸 기준으로 또 추측한다.

Forbidden
  • 없는 값을 임의로 정하고 진행하기
  • 다른 화면에서 쓰는 값을 근거 없이 복사하기
  • "일단 이렇게 두고 나중에" — 나중은 오지 않는다
Do this
  • §7 미결 목록에 추가하고 사람에게 질문한다
  • 답을 못 받고 진행해야 하면 가정한 값을 명시한다
  • §7에 이미 있는 항목이면 그 결정을 먼저 받는다
0.4

완료 전 자기점검

실측 항목

전부 브라우저에서 수치로 확인 가능한 항목이다. 확인한 값을 보고에 적는다.

  • 모달 내부 폼 컨트롤 0개
  • alert() confirm() prompt() 0회
  • 토스트 3초 자동 소멸
  • 텍스트 컨테이너 break-keep
  • 금액·수량 셀 tabular-nums + 우측 정렬 + 3자리 콤마
  • 배지·태그·버튼 flex-shrink:0 + nowrap
  • 캔버스 #F9FAFB · 카드 1px #E5E7EB · r12
  • 인터랙티브 최소 높이 40px(모바일 44px)
  • 테이블 행 36–40px(모바일 카드 48px+)
  • 비동기 발송·신고 버튼 disabled + 스피너
  • 서체 Spoqa Han Sans Neo 1종 · 웨이트 400/500/700
  • 가로 스크롤 0px · 상시 설명문 2줄 미만
  • 채움률 — 마지막 줄 제외 모든 줄이 컨테이너 폭 90% 이상
  • 마지막 줄에 한 음절만 남지 않음
  • 폭 상한을 ch로 지정하지 않음(한글은 1em)
  • 모든 상태를 펼친 뒤 실측 — 숨은 단계·토스트·에러
  • 같은 컬럼 블록의 좌우 끝 일치(left·right 각 1개 값)
  • 배경 채움 버튼이 화면당 1개
  • 첫 화면 빈 공간 40% 이하
  • 짧은 의미 단위(≤14자)가 줄바꿈으로 쪼개지지 않음
0.5

완료 보고에 반드시 적을 것

3줄
  • 분류 — 이 화면을 §2의 어느 패턴으로 만들었는지.
  • 적용 조항 — §1~§5 중 실제로 걸린 조항 번호. §5 방지책은 어느 것을 선탑재했는지.
  • 가정한 값 — 규격에 없어서 스스로 정한 값이 있으면 전부. 없으면 "없음"이라고 적는다.
§1 · CONSTITUTION

공통 헌법 — 모든 화면에서 예외 없이

새 페이지나 컴포넌트를 만들 때 아래 9개 조항은 타협 대상이 아니다.

1.1

무중단 흐름성공·저장 완료·복사 완료·네트워크 지연 모두 토스트로 전달한다. 닫기 클릭을 강제하지 않는다.

Non-disruptive
  • 작업 결과는 화면을 가로막지 않는 토스트로 전달하고 3초 후 자동 소멸시킨다.
  • 브라우저 기본 팝업 alert() confirm() prompt() 사용은 전면 금지.
1.2

모달 제약 및 인풋 전면 금지모달의 유일한 허용 목적: 영구 삭제, 국세청 즉시 신고 확정 등 불가역 파괴 액션의 2버튼 확인(Yes/No).

Hard rule

모달 안 입력창은 작성 중 이탈 시 데이터 유실 · 뷰포트 스크롤 꼬임 · 모바일 키보드 가림을 유발한다. 설계 취향 문제가 아니라 시스템 차원에서 차단하는 항목이다.

Forbidden
  • 모달 다이얼로그 내부 <input> <textarea> <select> 구현
  • 모달 안 거래처 추가 · 품목 등록 팝업
Use instead
  • 인라인 편집 — 단일·소량 수정 (테이블 셀)
  • 슬라이드오버 시트 — 복합·보조 입력 (우측 드로어)
  • 독립 포커스 페이지 — 견적서·세금계산서 빌더
1.3

점진적 정보 노출

Zero clutter
  • 폼 필드 아래나 카드 상단에 2줄 이상 상시 안내 문구를 배치하지 않는다.
  • 보조 설명은 라벨 우측 16px HelpCircle (?) 아이콘의 툴팁·팝오버로 캡슐화한다.
  • 이 페이지의 (?) 아이콘 13개가 그 패턴의 구현 예다.
1.4

타이포그래피 및 금융 데이터 표기

Typography
  • 제목·본문·UI 전반 Spoqa Han Sans Neo 단일화. 명조(세리프)·필기체 금지.
  • 웨이트 사다리는 400 / 500 / 700만 쓴다. Spoqa에는 600이 없으므로 font-weight:600은 500으로 내린다.
  • 코드·토큰 문자열만 시스템 모노(ui-monospace)를 허용한다. 본문 서체로 코드를 쓰면 열 정렬이 깨진다. 웹폰트는 추가하지 않는다.
  • 모든 텍스트 컨테이너에 word-break: keep-all overflow-wrap: break-word (Tailwind break-keep).
  • 금액·수량·세액 셀은 font-variant-numeric: tabular-nums + text-right + 3자리 콤마(1,250,000원).
  • Spoqa Han Sans Neo에는 tnum 피처가 없다. 대신 숫자 자체가 고정폭(400·500·700 모두 596/1000em 실측)이라 결과는 동일하다. 선언은 폴백 서체를 위해 유지한다.
  • 본문은 컨테이너 폭을 채운다검증은 Range.getClientRects()로 한다. 인라인 박스의 세로 중심을 line-height의 60% 오차로 묶어야 한다 — top으로 묶으면 code의 패딩 때문에 한 줄이 둘로 세어진다. — 마지막 줄을 제외한 모든 줄이 컨테이너 폭의 90% 이상이어야 한다. 그보다 낮으면 폭 상한이 잘못 걸린 것이다. 마지막 줄이 짧은 것은 좌측 정렬에서 정상이다 — 다만 한 음절만 남으면 결함이고, text-wrap: pretty가 이를 방지한다.
  • 한글 폭을 ch로 재지 않는다. ch는 숫자 글리프 폭 기준이고 Spoqa Han Sans Neo에서 0.596em이다. 한글은 1em이다. 그래서 max-width:46ch는 한글 27자 — 의도한 46자의 60%밖에 안 된다. 폭 상한이 필요하면 em이나 px로 지정한다.
  • text-wrap: balance를 본문에 쓰지 않는다. balance는 가장 긴 줄을 줄여 모든 줄을 짧게 만든다 — 채움률과 정면 충돌한다. 2~3줄짜리 표제에만 허용한다.
  • 짧은 의미 단위는 쪼개지 않는다 — 조항 참조(§0 작업 개시 규칙) · 수치+단위(36–40px) · 금액(1,250,000원) · hex(#F9FAFB)는 white-space: nowrap으로 묶는다. 공백 포함 14자까지만 — 그보다 길면 묶지 않는다. 좁은 화면에서 넘친다.
  • break-keep은 단어 안을 보호할 뿐, 구(句)가 줄바꿈으로 쪼개지는 것은 막지 못한다. 금지 #05의 방지책만으로는 부족하다.

Layout integrity

지표 한 칸에는 값 하나만 넣는다. 큰 숫자 옆에 다른 지표를 붙이면 무엇이 주 값인지 사라진다.

Forbidden
  • 한 칸에 지표 둘 — 6건 합계 35,328,000원
  • 성격이 다른 지표를 같은 행에 나열 — 업무량(건수·금액)과 소요 예측(3분)은 다른 종류다
  • 큰 값 뒤에 작은 라벨을 같은 줄에 붙여 위계를 뭉개기
Do this
  • 한 칸 = 라벨 하나 + 값 하나
  • 지표 행은 같은 종류·같은 단위만 묶는다
  • 종류가 다르면 행을 나누거나 문장으로 쓴다
  • 같은 컬럼의 모든 블록은 좌우 끝이 정확히 일치한다. 실측으로 확인한다 — 컬럼 안 블록들의 left 값이 하나여야 하고, right 값도 하나여야 한다. 카드 내부 요소는 카드 패딩만큼 들어가는 것이 정상이다.
  • 브라우저 기본 여백을 리셋에서 빠뜨리지 않는다. <ol>은 padding-inline-start: 40px이 기본값이다. ul만 리셋하면 ol 행 하나가 40px 밀려 좌우 단차가 생긴다. ul,ol,dl,dd,figure,fieldset을 함께 리셋한다.
  • 콘텐츠가 뷰포트를 채운다. 첫 화면에서 빈 공간이 세로 40%를 넘으면 화면 유형 분류(§2)가 틀린 것이다. 3-Pane 을 단일 흐름에 쓰면 폭이 남는다.
  • 아무것도 못 하는 컨트롤은 숨긴다. 되돌릴 게 없으면 되돌리기 버튼을 disabled 로 두지 말고 없앤다(§1.8).

§4 · DIVERGENCE

의도적 차이 vs 정리 후보

다르게 생긴 화면은 두 종류다. 정당한 분기이거나, 아직 못 갚은 부채다. 섞어두지 않는다.

의도적 차이

정당한 분기
  • 인터랙션 — 데스크톱은 3패널 Co-planar + 우측 슬라이드 드로어, 모바일(<768px)은 하단 탭바 + 바텀 시트.
  • 테이블 밀도 — 데스크톱 36px 고밀도 행 유지, 터치 환경은 최소 48px 카드 리스트 뷰로 대체.

정리 후보

기술 부채
  • 레거시 모달 폼 전수 제거 — 초기 버전의 '모달 내부 거래처 추가·품목 등록' 팝업을 우측 슬라이드오버 시트로 순차 교체.
  • 인라인 스타일 변수 통일 — 하드코딩 색상값(#333 #222)을 디자인 토큰(text-gray-900 text-gray-600)으로 일괄 리팩터링.

# Z to Sigma (Paywork) Frontend Constitution & Rules

## 0. Before You Start (READ THIS FIRST)
- TRIGGER: any new screen/service, any menu improvement, any new component, any layout or
  density change, any transaction-document UI. If it renders, this applies.
- Do NOT write UI code before you have (a) picked the screen pattern and (b) read §1 of the UX guide.
- Order: 1) classify screen type → 2) lock document state badges/CTA → 3) apply the 5 constitution
  rules → 4) pre-load the incident guards → 5) verify the self-check list by measurement.
- If a spec value is MISSING: never invent one. Add it to the open-items list and ask.
  If you must proceed, state the assumed value explicitly in your report.
- Report must state: which screen pattern, which rule sections applied, which values you assumed.
- 전문: docs/UX_GUIDE.md §0. 이 절은 그 요약이다.

## 1. Absolute Constraints (Zero Tolerance)
- FORBIDDEN: NEVER build form controls (`<input>`, `<textarea>`, `<select>`) inside Modal Dialogs.
- Modals are strictly for two-button confirmation of irreversible destructive actions (Delete, Final IRS Submit).
- For form inputs, use: (1) Inline editable cells, (2) Right-side Slide-over Sheets, or (3) Dedicated full pages.
- NEVER use native blocking alerts (`window.alert`, `window.confirm`). Use Toast notifications (auto-dismiss 3s).

## 2. Korean Typography & Numeric Rules
- All Korean text containers MUST include `word-break: keep-all; overflow-wrap: break-word;` (Tailwind: `break-keep`).
- `break-keep` protects inside a word only. It does NOT stop a phrase from splitting across
  lines, and it does nothing about line fill.
- Body text MUST fill its container: every line but the last at 90%+ of container width.
  Below that, a width cap is wrong. A short last line is normal; a single-syllable last line is a defect.
- NEVER measure Korean measure in `ch`. In Spoqa Han Sans Neo `1ch` = 0.596em while a Hangul
  glyph is 1em, so `max-width:46ch` yields 27 Korean characters — 60% of what you intended. Use `em` or px.
- NEVER use `text-wrap: balance` on body text. It shrinks the longest line, making every
  line short — the opposite of filling the container. Use `text-wrap: pretty`. Balance is for 2-3 line headings only.
- Wrap short semantic units in `white-space: nowrap`: section refs (`§0 작업 개시 규칙`), number+unit (`36-40px`),
  money (`1,250,000원`), hex (`#F9FAFB`). 14 characters max, spaces included — longer units
  must be allowed to break or they overflow narrow screens.
- Font family is strictly `Spoqa Han Sans Neo` (SIL OFL 1.1). No serif/cursive fonts.
- Weight ladder is 400 / 500 / 700 only. Spoqa has no 600 — map `font-weight:600` to 500.
- Only code/token strings may use `ui-monospace`. Never add another webfont.
- Financial numbers in tables/cards MUST use `font-variant-numeric: tabular-nums`, right alignment (`text-right`),
  and 3-digit commas (`1,000,000원`).

## 3. Zero Clutter & Progressive Disclosure
- NEVER render multi-line static explanatory text directly under labels.
- Secondary descriptions MUST be wrapped inside a 16px `HelpCircle` icon triggering a Tooltip or Popover.

## 4. Visual Tokens & Surface Language
- Canvas Background: `#F9FAFB` (Off-white canvas). Pure white `#FFFFFF` for page background is prohibited.
- Cards & Surfaces: `#FFFFFF` with `border: 1px solid #E5E7EB` and `border-radius: 12px`. Drop shadows minimal.
- Touch Targets: Interactive elements must have a minimum height >= 40px (Mobile >= 44px).
- Badges & Tags: Always set `flex-shrink: 0; white-space: nowrap;` to prevent layout collapse.
- Light theme ONLY. Declare `color-scheme: light`. Never add a dark palette or `prefers-color-scheme` block.
- Brand colors: Paywork Navy `#072436` (PANTONE 289 C) and Paywork Green `#10DE52` (PANTONE 2270 C).
- Primary CTA is ALWAYS Navy `#072436` fill with white text. Focus ring is 2px Navy — never the
  browser default blue.
- NEVER use Paywork Green as a button background. The brand defines Green as
  "confirmed / completed / resolved", which is exactly what Paid and Reported mean in the state machine.
  A green CTA on a Draft screen destroys the green-means-done mapping. Green is for status and success feedback only.
- Destructive actions use Red `#FF5277` fill with NAVY text (not white), and only alongside
  the two-button confirmation modal. Measured: white on that red is 3.12:1 (fails AA), Navy is 5.12:1 (passes).

## 8. Interaction States (§1.7)
- Never invent a state color. Step down the existing neutral ladder:
  surface hover `#F3F4F6` → pressed `#E5E7EB`; primary hover `#0E3852` → pressed `#04161F`.
- Declare hover only inside `@media (hover: hover)`. On touch devices a hover style sticks after tap.
- Use `:focus-visible` only, never `:focus`. Transition `background-color 120ms ease` — never layout properties.
- DISTINGUISH disabled from loading. Loading keeps the button's own background and adds a
  spinner; turning it grey mid-request looks broken.

## 9. Screen States — Empty / Loading / Error (§1.8)
- One question decides toast vs screen state: is there data to show on this screen?
  Yes → toast, leave the screen alone. No → replace the region with a screen state. Never a toast on an empty screen.
- Loading uses skeletons, not spinners (spinners only inside buttons and regions under 400px).
  Delay the skeleton by 200ms — flicker is worse than waiting. Mirror the real layout so
  nothing shifts on load.
- Empty state has THREE variants, never one: first-run (has a primary CTA), no-results (reset-filter only,
  echo the query back), all-clear (no CTA, Paywork Green allowed). Green on first-run reads as "done" — forbidden.
- Errors: 5xx/timeout → "Retry" primary. 403 → no retry button, it will not work. 404 → back to list.
- Never print stack traces or status codes. Print a request ID in `mono 11px` instead.
- Error copy: what failed + what to do, two sentences max. Never "An error occurred". No apologies.
- Partial failure replaces only that region. A failed sidebar must not blank the main content.

## 10. Layout Integrity (§1.9)
- One stat cell holds one value. Never `6건 합계 35,328,000원` in a single cell — the reader
  cannot tell which number is the point. Never mix kinds in one row (workload vs time estimate).
- Every block in a column MUST share one `left` and one `right`. Verify by measurement, not by eye.
- RESET `ol` TOO. `
    ` ships with `padding-inline-start: 40px`. Resetting only `ul`
  pushes that one row 40px inward and produces a visible misalignment. Reset `ul,ol,dl,dd,figure,fieldset`.
- Background fill is for the primary CTA only — one per screen. A selected option or toggle
  with the same Navy fill reads as a second primary action. Selected state = `#F3F4F6` + Navy text + weight 500.
- If empty space exceeds 40% of the first viewport, the screen-pattern choice (§2) is wrong, not the content.

## 5. Defensive Engineering & Safety
- Currency inputs must safely strip commas before numeric parsing to prevent `NaN` bugs.
- API submission buttons MUST implement debounce and display loading spinners with `disabled` states.
- Long-form document editors must feature automatic local draft saving.

> 아래 6·7절은 원문 룰셋 블록에 없던 확장이다. 본 문서 §3·§2에서 파생했다.

## 6. Document State Machine
- Draft → Sent → Viewed → Signed → Paid → Reported
- Badge tokens are fixed per state; do not invent new status colors.
  Draft    bg-gray-100 / text-gray-700       Signed   bg-teal-50 / text-teal-700
  Sent     bg-blue-50 / text-blue-700        Paid     bg-emerald-50 / text-emerald-700
  Viewed   bg-purple-50 / text-purple-700    Reported bg-green-100 / text-green-800

## 7. Layout Density
- Dashboard / Ledger screens: >=1280px, 64px global rail + 280px list + main, table rows 36-40px.
- Focused Document screens: 760-840px centered, input height 40-44px, single primary CTA in header.
- Mobile (<768px): bottom tab bar + bottom sheet, card list rows >=48px.
§7 · OPEN ITEMS

초안 미결 항목규격이 비어 있으면 개발자와 에이전트가 각자 추측한다. 추측이 들어간 지점부터 구현 편차가 시작된다.

본 초안에 값이 없어 구현자가 스스로 판단하게 되는 지점이다. 이 섹션은 확정 규격이 아니라 검토 요청 목록이다.

OPEN-01

기존 paywork-ia-visual Skill과 토큰 충돌

선택 필요

인터콤 실측 기반 Skill은 backdrop #EFF0EB · radius 16/12/8/6 사다리 · 행 50px · 버튼 32px을 규정한다. 본 문서는 캔버스 #F9FAFB · radius 12 단일 · 행 36–40px · 터치 타깃 40px이다. 두 문서가 동시에 SSOT일 수 없다.

①안 · 본 문서를 SSOT로Tailwind 계열 토큰으로 통일하고 Skill 실측값을 재정렬. shadcn 기본값과 맞물려 구현이 빠르다.
②안 · Skill 실측값 유지인터콤 레퍼런스 정합성을 보존하고 본 문서 토큰을 교체. 이미 만든 스켈레톤 4종을 버리지 않는다.
OPEN-04

상태 머신에 실패·역행 경로 없음

Draft→Reported 정방향만 있다. 발송 실패, 신고 반려, 취소·무효, 연체(기존 IA 문서에는 존재)의 배지와 CTA가 비어 있다.

OPEN-05

타이포 스케일 · 스페이싱 단위 수치 없음

서체와 줄바꿈 규칙은 있으나 사이즈·웨이트 사다리와 간격 단위(4px/8px)가 없다. 화면마다 제목 크기가 달라질 여지가 남는다.

OPEN-06

16px (?) 아이콘 vs 터치 타깃 40px 내부 충돌

§1.3은 16px 아이콘을, §1.5는 최소 40px 터치 타깃을 요구한다. 히트 영역 확장 규격(패딩 몇 px까지 허용)이 없다. 이 페이지는 padding:6px; margin:-6px로 28px 히트 영역을 썼다 — 규격이 아니라 임시 판단이다.

선택 필요
OPEN-10

§3 상태 배지가 브랜드 팔레트 밖에 있다

선택 필요

§1.6으로 브랜드 팔레트가 확정되면서 §3 배지 6종이 어긋났다. Tailwind 값이라 브랜드 정의서에 없고, 특히 Viewed의 purple 계열은 브랜드 팔레트에 아예 없는 색이다. 제약이 하나 있다 — 브랜드 팔레트에 배지 배경용 저채도 틴트가 Green 계열에만 있다(10~90%). Blue는 가장 밝은 값이 #8DCCFF로 아직 진하고, Gray는 #CCCCCC 단일 값뿐이다. 그대로 매핑할 수 없고 틴트를 새로 파생해야 한다.

①안 · 브랜드 틴트를 파생해 재매핑Blue·Gray·Teal에 Green과 같은 10~90% 틴트 스케일을 만들고 배지 6종을 브랜드 색으로 교체한다. 브랜드 정합성은 완전해지지만 파생값을 브랜드 정의서에 역등록해야 한다.
②안 · 상태 색은 기능 색으로 분리 유지배지는 Tailwind 값을 유지하고, §1.6에 "상태 색은 브랜드 팔레트와 별개 체계"라고 명시한다. 지금 구현을 안 건드리지만 purple은 여전히 근거가 없다.
OPEN-11

브랜드 Option 팔레트에 Red 단계가 없다

§1.7에서 파괴적 버튼의 hover·pressed를 filter: brightness(.94/.88)로 처리했다. 브랜드 정의서의 Red가 #FF5277 단일 값이라 새 색을 만들지 않으려는 임시 처리다. 실측으로 확인된 제약도 있다 — Red 배경에 흰 텍스트는 대비 3.12:1로 AA 미달이고, Navy 텍스트가 5.12:1로 통과한다. 정의서에 Red 단계(또는 텍스트용 진한 Red)를 추가할지는 브랜드 쪽 결정이다.

§1.3 · §2 밀도 규격은 앱 화면을 전제로 쓰였고 적용범위 한정이 없다. 그래서 문서 페이지는 지킬 방법이 없다. 같은 문제가 앞으로 랜딩·리포트·대시보드마다 반복된다.

①안 · 규격을 문서에도 강제테이블 패딩 축소해 40px 이하로, 카드 상단 prose를 (?) 툴팁으로 이관, 히트 영역 40px. 페이지가 규격의 증거가 된다. 문서 가독성은 일부 손해.
②안 · 규격에 적용범위 조항 추가§1.3을 폼 필드 헬프텍스트 한정, §2 밀도를 원장·목록 화면 한정, §1.5에 인라인 아이콘 예외(28px) 명시. 규격이 화면 유형별로 정확해진다.
